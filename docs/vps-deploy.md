# Отдельный сервер магазина и автоматическая выкладка (NAP-087)

Магазин store.napsystem.com работает на **собственном сервере**, независимо от napsystem.com.
Код живёт только в GitHub, образы собирает GitHub Actions, сервер их только скачивает и запускает.
Ни Мак, ни сервер платформы в цепочке не участвуют.

```
ветка → PR → CI (тесты, e2e, Docker, vps-acceptance) → автопринятие в master
      → CI master → последний job CI вызывает deliver-vps: сборка образов backend/web amd64+arm64 (кэш слоёв) → GHCR по digest
      → SSH на сервер (ключ может запускать только napdeploy.py)
      → дамп БД → миграции → переключение → проверка готовности → при ошибке возврат предыдущего выпуска
```

## Что нужно один раз (владелец)

1. **Сервер.** Ubuntu 24.04, от 2 vCPU / 4 ГБ RAM / 40+ ГБ SSD, Hetzner Cloud в Германии (решение владельца,
   NAP-097). Образы собираются под x86 (amd64) и Arm (arm64), подходит любой тип; рабочий сервер — CAX21
   (4 Ampere, 8 ГБ, 80 ГБ, Falkenstein). При покупке добавьте свой SSH-ключ (`~/.ssh/id_ed25519.pub`),
   либо после покупки: `ssh-copy-id -i ~/.ssh/id_ed25519.pub root@IP`.
2. **Установка (одна команда с Мака):**
   ```
   ssh root@IP 'bash -s' < nap-vps-install.sh
   ```
   Файл собирается командой `python3 ops/vps/make-installer.py` (bootstrap.sh + napdeploy.py в одном файле).
   Установщик: обновления и автообновления безопасности, firewall (22/80/443), fail2ban, swap 2 ГБ, Docker,
   пользователь `napdeploy`, `/srv/nap-store`, файл настроек `shared/.env` со **сгенерированными на сервере**
   паролями (никуда не передаются), ключ выкладки, отключение входа по паролю (если у root есть ключ).
   Повторный запуск безопасен: .env, данные и ключ сохраняются.
3. **GitHub** → ma5ter77/napsystem_store → Settings → Secrets and variables → Actions (значения печатает установщик):
   - Variables: `STORE_DEPLOY_HOST` (IP), `STORE_DEPLOY_HOST_KEY` (`ssh-ed25519 AAAA…`). Это не секреты.
   - Secrets: `STORE_DEPLOY_SSH_KEY` — приватный ключ выкладки. **Только в GitHub, никому не пересылать.**
4. **DNS (REG.RU):** A-запись `store` → IP нового сервера. Сертификат Let's Encrypt Caddy получит сам.
5. **Первый запуск:** Actions → deliver-vps → Run workflow (или любой следующий merge в master: выкладку
   вызывает последний job CI на master, после `ci-ok`).

Необязательно: ручное подтверждение каждой выкладки — Settings → Environments → production →
Required reviewers. Без этого выкладка полностью автоматическая.

## Повседневная работа

| Что | Как |
|---|---|
| Выложить | ничего: принятый PR → master → сервер (~10–15 мин) |
| Выложить конкретный коммит | Actions → deliver-vps → Run workflow → sha |
| Состояние, логи | Actions → store-ops → status / logs (сервис) |
| Откат на предыдущий выпуск | Actions → store-ops → rollback |
| Изменить настройки (ключи Stripe, SMTP…) | на сервере `sudo -u napdeploy nano /srv/nap-store/shared/.env`, затем store-ops → restart |
| Резервная копия сейчас | store-ops → backup (ежедневно автоматически в 23:30 UTC, с проверкой восстановления) |

Claude запускает эти же действия через GitHub API и читает результат в отчёте workflow — без SSH-доступа.

## Демо-аккаунты на публичном сервере

Пароль `demo-password-1` из документации и превью на публичном сервере **не работает**. Аккаунты `*@nap.demo`,
в том числе `admin@nap.demo`, получают собственный пароль сервера. Он вычисляется из `NAP_SECRET_KEY`, который
никогда не покидает сервер. Если в `shared/.env` задан `NAP_DEMO_PASSWORD`, используется он. Каждая выкладка
переводит аккаунты, оставшиеся на документированном пароле, на пароль сервера и завершает их сессии.

Узнать пароль (только в своём терминале):

```
ssh root@IP 'docker exec $(docker ps -q -f label=com.docker.compose.service=api | head -1) python -m app.tools.demo_password'
```

Перед запуском с реальными покупателями демо-данные выключаются (`NAP_SEED_DEMO=0`, `NAP_ENV=production`).

## Безопасность

- Ключ выкладки в `authorized_keys` ограничен: `command="… napdeploy.py gate",restrict` — только
  deploy / rollback / restart / status / logs / backup; без shell, проброса портов и агента.
- Ключ сервера закреплён (`STORE_DEPLOY_HOST_KEY`): подмена сервера останавливает выкладку.
- Образы принимаются только из `ghcr.io/ma5ter77/nap-store-*` и только по digest; токен для скачивания —
  временный GITHUB_TOKEN задания, на диске сервера не сохраняется.
- napdeploy.py проверяет compose: запрещены privileged, cap_add, devices, host network/pid/ipc, монтирование
  вне каталога выпуска и backups, публикация портов кроме Caddy. Файлы набора выпуска — по списку.
- Секреты приложения есть только в `/srv/nap-store/shared/.env` (600, владелец napdeploy).
- Логи в отчёте: строки, похожие на секреты, вырезаются.

## Правила для миграций

Откат не понижает схему БД. Поэтому миграции **совместимы назад**: сначала добавить (колонку, таблицу),
убрать старое — следующим выпуском. Неудачная миграция откатывается транзакцией PostgreSQL, выпуск не
включается. Перед каждой миграцией делается дамп `backups/pre-deploy-*.dump` (последние 5); восстановление
из дампа — отдельное ручное действие.

## Ресурсы

Лимиты памяти рассчитаны на 4 ГБ: postgres 768M, api 768M, worker-media 1G (1,5 CPU), worker-ops 512M,
web 512M, redis 192M, caddy 128M, backup 256M, плюс swap 2 ГБ. На сервере ничего не собирается.
Хранятся последние 5 выпусков (файлы и образы), старые удаляются автоматически.

## Минуты GitHub Actions

Каждый merge: CI (~15 мин) + образы (amd64 и arm64; arm64 собирается в эмуляции: ~10–20 мин с кэшем,
первая сборка до ~60 мин) + выкладка (~2–4 мин). В бесплатном лимите
приватного репозитория (2000 мин/мес) это ~50–60 выкладок в месяц. Изменения только в docs/ тоже проходят CI.

Эксплуатация и аварии — [OPERATIONS.md](../OPERATIONS.md), стоимость — [COSTS.md](../COSTS.md).
