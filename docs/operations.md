# Эксплуатация

## Здоровье, логи, метрики

- `GET /api/v1/health` — процесс жив; `GET /api/v1/ready` — БД (и номер миграции), Redis, хранилище; `503`, если что-то недоступно.
- `GET /api/v1/metrics` (Prometheus text): запросы, ошибки 4xx/5xx, суммарная длительность, задания конвертации по состояниям, средняя длительность конвертации, необработанные webhooks, неотправленные outbox-задачи.
- Логи — JSON в stdout с `request_id` (заголовок `X-Request-Id` возвращается клиенту и попадает в аудит и тексты ошибок) и `job_id`; подписанные URL, токены, адреса, телефоны и ответы анкет в логи и аудит не пишутся.
- Админка → «Эксплуатация»: очереди, проблемные webhooks, ручной запуск обработки inbox/outbox/резервов/lease/сверки, контроль пропусков словарей.

## Фоновые задачи (Celery beat, очередь `ops`)

| Задача | Период |
|---|---|
| Обработка inbox webhooks (повтор событий «не по порядку») | 30 с |
| Отправка outbox (возвраты, выплаты, уведомления, передача поставщику) | 15 с |
| Восстановление заданий с истёкшим lease | 60 с |
| Освобождение просроченных резервов склада | 60 с |
| Сверка зависших оплат с провайдером | 10 мин |
| Удаление измерений по сроку хранения | сутки |

Конвертации идут в очереди `media` на отдельном воркере (в compose — только внутренняя сеть, лимиты CPU 2 / RAM 3 ГБ).

## Резервное копирование и восстановление

```bash
ops/backup.sh postgresql://nap:nap@localhost:5432/nap ./backups              # pg_dump -Fc + .sha256
ops/restore_verify.sh ./backups/nap-….dump <SOURCE_URL> <ADMIN_URL>           # восстановление в scratch-БД и сверка
```

Проверено 31.10.2026: восстановление в чистую базу дало совпадение счётчиков пользователей, приложений, версий, заданий, assets, заказов, посылок, проводок, суммы журнала (= 0), аудита и остатков; миграция 0002; триггеры неизменяемости журнала и аудита восстановились. Перезапуск PostgreSQL и API не меняет данные. Объекты хранилища (S3/MinIO) копируются средствами хранилища (версионирование бакета / `mc mirror`); ключи объектов в БД остаются валидными.

Рекомендуемая политика: ежедневный `pg_dump` + WAL-архивирование для PITR, хранение 30 дней, ежемесячная проверка `restore_verify.sh`.

## Benchmark конвертации (фактический)

Среда: 2 vCPU Intel Xeon 2,1 ГГц, 7,8 ГБ RAM, Python 3.13, FFmpeg 6.1.1, профиль `alpha-demo-v1`, одна конвертация за раз, синтезированный стерео-вход. Сырые данные: `docs/qa/benchmark.json`.

| Вход | Длительность | Время обработки | Быстрее реального времени | CPU Python / ffmpeg | Пиковая память конвейера | Мастер WAV / FLAC |
|---|---|---|---|---|---|---|
| WAV 16 бит 44,1 кГц | 10 мин | 24,4 с | ×24,6 | 16,5 с / 8,2 с | 265 МБ | 173 МБ / 131 МБ |
| WAV 16 бит 44,1 кГц | 60 мин | 128,8 с | ×28,0 | 87,0 с / 44,5 с | 275 МБ | 1037 МБ / 786 МБ |
| MP3 192 кбит/с | 10 мин | 22,9 с | ×26,2 | 15,3 с / 7,9 с | 264 МБ | 173 МБ / 127 МБ |
| WAV 16 бит 44,1 кГц | **120 мин** | **309,1 с (5 мин 9 с)** | ×23,3 | 221,3 с / 94,8 с | 291 МБ | 2074 МБ / 1573 МБ |

Память не зависит от длительности (обработка блоками по 65 536 кадров). При профилировании найдено и исправлено: QA-анализ частот брал 60 с слоя с 8× дополнением нулями (~1 ГБ); теперь 10 с (точность та же, пик 1011 → 261 МБ). Временный диск на 120-минутный файл: ≈ 2,8 ГБ spool float32 + 2,1 ГБ мастер + ≈ 1,6 ГБ FLAC; свободное место проверяется до декодирования. 120 минут измерены 01.11.2026 (NAP-054): 5 мин 9 с на 2 vCPU, пик памяти 291 МБ — память по-прежнему не растёт с длительностью; прежняя оценка по экстраполяции (≈ 4,5 мин) оказалась занижена на ~15 % из-за ввода-вывода на файлах в несколько ГБ. На сервере 2 vCPU / 4 ГБ (docs/vps-deploy.md) worker-media ограничен 1 ГБ и 1,5 CPU — одновременно безопасна одна длинная конвертация; время для 120 минут там ожидается ≈ 6–7 мин.

## Ограничение частоты запросов (NAP-052)

Окна фиксированной длины в Redis (при недоступном Redis — счётчики в процессе API). Ключ — пользователь, без входа — адрес клиента (первый `X-Forwarded-For` за прокси Next.js/Caddy). При превышении — `429 rate_limited` с текстом на языке запроса и заголовком `Retry-After`. `/health`, `/ready`, `/metrics`, `/version` не ограничиваются.

| Лимит | По умолчанию |
|---|---|
| `global` — любой запрос к API | 1200 в минуту |
| `upload_ticket` — новые ссылки загрузки | 60 в час |
| `upload_chunk` — части файла по 8 МБ | 900 в минуту |
| `checkout` — оформление цифровых и аппаратных заказов, тестовая оплата | 30 за 10 минут |
| `webhook` — вебхуки платёжного провайдера и перевозчика, на адрес | 600 в минуту |
| `review_write`, `review_report` — отзывы, ответы, жалобы | 30 и 20 в час |
| `conversion` — запуск конвертаций | 60 в час |

Переопределение: `NAP_RATE_LIMITS="checkout=10/600,global=600/60"`; выключение — `NAP_RATE_LIMITS_ENABLED=false`.

## CI (NAP-003)

`.github/workflows/ci.yml`: `backend` (pytest + `alembic check`), `frontend` (словари, шаблоны полей, типы, сборка), `e2e` (полный стек, сценарии RU/EN, скриншоты и логи в артефактах), `docker` (сборка и запуск compose до `/ready`), `ci-ok`. В настройках репозитория (Branch protection → Require status checks) отметьте `ci-ok` обязательной проверкой — тогда пулреквест не сливается при красном CI.

## Отправка писем (NAP-007)

Уведомления (оплата, подписка, модерация, ответы на отзывы, заказы оборудования) рендерятся на языке получателя и попадают в outbox; воркер `ops` отправляет их и отмечает `notifications.emailed_at`. Одно уведомление — одно письмо (ключ `X-NAP-Ref`), повтор при сбое с экспоненциальной паузой 30 с … 1 ч (до 20 попыток).

| `NAP_EMAIL_BACKEND` | Что происходит |
|---|---|
| `log` (по умолчанию) | письмо пишется в журнал воркера — для демо |
| `file` | `.eml`-файлы в `/app/var/mail` — удобно для тестового стенда |
| `smtp` | любой SMTP-провайдер: `NAP_SMTP_HOST`, `NAP_SMTP_PORT` (587 STARTTLS / 465 SSL), `NAP_SMTP_USER`, `NAP_SMTP_PASSWORD`, `NAP_SMTP_SECURITY` |

Для production отправителю нужны SPF, DKIM и DMARC на домене `NAP_EMAIL_FROM`. Метрики: `nap_emails_failed`, `nap_outbox_stuck`.

## Ежедневный бэкап с проверкой восстановления (NAP-006)

Сервис `backup` в `docker-compose.yml` каждый день в `BACKUP_AT` (UTC, по умолчанию 02:30):
1. `pg_dump` в `./backups/nap-YYYYMMDDTHHMMSSZ.dump` + контрольная сумма;
2. восстановление дампа во временную базу и сверка с источником: количество строк ключевых таблиц, сумма журнала проводок, версия миграции, наличие триггеров неизменяемости (`ops/restore_verify.sh`);
3. архив файлового хранилища (`storage-*.tar`) — аудио, обложки, документы;
4. удаление файлов старше `BACKUP_KEEP_DAYS` (14);
5. итог в `./backups/last-status.json` — его читает API: `/metrics` (`nap_backup_ok`, `nap_backup_age_seconds`, `nap_backup_size_bytes`) и «Администрирование → Эксплуатация».

Ручной запуск: `docker compose exec -e BACKUP_ONCE=1 backup bash /ops/backup-loop.sh`. Восстановление из дампа: `pg_restore --clean --no-owner -d <URL> backups/nap-….dump`, файлов — `tar -xf backups/storage-….tar -C <том storage>`.
Копии на том же сервере не защищают от потери сервера: синхронизируйте `./backups` во внешнее хранилище (S3/другой сервер, NAP-004).

## Мониторинг и оповещения (NAP-005)

`docker compose --profile monitoring up -d` поднимает Prometheus (UI на `127.0.0.1:9090`, хранение 30 дней) и Alertmanager. Правила — `ops/monitoring/alerts.yml`:

| Оповещение | Условие |
|---|---|
| `NapApiDown` | API недоступен 2 мин |
| `NapHigh5xxRate` | > 10 ответов 5xx за 10 мин |
| `NapConversionsFailing`, `NapConversionQueueStuck` | > 3 неудачных конвертаций в час; очередь > 20 дольше 15 мин |
| `NapWebhooksBacklog` | вебхуки оплат/доставки не обработаны 30 мин |
| `NapOutboxStuck`, `NapEmailsFailing` | исходящие события повторяются 5+ раз; письма не доставляются 30 мин |
| `NapBackupFailed`, `NapBackupStale`, `NapBackupMissing` | бэкап не удался; старше 26 ч; нет данных |

Оповещения уходят письмом: заполните `ops/monitoring/alertmanager.yml` (адрес получателя и SMTP). CI проверяет обе конфигурации `promtool`/`amtool`.

## Хранилище файлов: локальный том или закрытый S3-бакет (NAP-004)

По умолчанию файлы (исходники, результаты конвертации, превью, этикетки) лежат на томе `storage`. Для боевого стенда — закрытый S3-бакет. Браузер никогда не обращается к бакету: файл отдаёт API по подписанной ссылке, действующей 5 минут (`NAP_SIGNED_URL_TTL_SECONDS`) (поддерживаются Range-запросы для перемотки).

**Вариант 1 — встроенный SeaweedFS** (`chrislusf/seaweedfs:4.45`, Apache-2.0; MinIO больше не подходит: проект в архиве с апреля 2026, образы удалены с Docker Hub в сентябре 2026). В `.env`:

```
COMPOSE_PROFILES=s3
NAP_STORAGE_BACKEND=s3
NAP_S3_ACCESS_KEY=<длинный случайный ключ>
NAP_S3_SECRET_KEY=<длинный случайный секрет>
```

Сервис `s3` работает только во внутренней сети compose, порт наружу не открыт, анонимный доступ выключен. Данные — том `s3data`; ежедневный бэкап архивирует его (`backups/storage-s3-*.tar`).

**Вариант 2 — внешний S3** (Hetzner Object Storage, Backblaze B2, AWS S3 и т. п.): `NAP_STORAGE_BACKEND=s3`, `NAP_S3_ENDPOINT_URL`, `NAP_S3_BUCKET`, `NAP_S3_REGION`, ключи; профиль `s3` не нужен. Включите версионирование бакета у провайдера — это и есть копия файлов вне сервера.

Бакет создаётся при первом запуске. Если у бакета есть политика, открывающая доступ всем, API не стартует (`/api/v1/ready` → 503). В production без собственного `NAP_S3_SECRET_KEY` сервис не запустится.

**Перенос существующих файлов с тома в бакет** (ключи в базе не меняются):

```
docker compose up -d                                   # уже с настройками S3 в .env
docker compose exec api python -m app.tools.storage migrate --from /app/var/storage --dry-run
docker compose exec api python -m app.tools.storage migrate --from /app/var/storage
docker compose exec api python -m app.tools.storage check
```

`migrate` копирует каждый файл под тем же ключом, сверяет размер и SHA-256 (для файлов приложений), повторный запуск ничего не копирует. `check` проверяет запись, чтение, Range, хэш, подписанную ссылку и то, что бакет не отвечает на анонимный запрос; код выхода 1 при любой проблеме. После успешного переноса том `storage` можно оставить как резервную копию на время приёмки.

Проверено: эмулятор S3 (moto) в тестах `test_s3_storage.py` — создание бакета, отказ на публичной политике, перенос демо-данных с проверкой хэшей и глубокая проверка целостности опубликованных версий из бакета; на настоящем SeaweedFS — шаг CI `switch to the private S3 bucket`.
