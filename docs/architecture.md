# Архитектура и принятые решения

## Компоненты

```
 браузер ── Next.js (App Router, SSR /ru /en) ──/api/v1 (rewrite, same-origin)──┐
                                                                               ▼
 SDK (TypeScript, сервер) ── Bearer napk_… ──────────────────────────► FastAPI /api/v1 (OpenAPI)
                                                                     │  ├─ сервисы (единственный владелец бизнес-логики)
 Stripe / EasyPost / mock ── webhooks (подпись на сыром теле) ──────►│  ├─ адаптеры: PaymentProvider, ShippingAdapter,
                                                                     │  │  FulfillmentAdapter, DeviceAdapter, измерения
                                                                     ▼
              PostgreSQL 16 (Alembic) ◄── Celery workers (Redis) ──► приватное S3 (MinIO) / локальное FS
                                          ├─ media: конвертация (без внешней сети, лимиты CPU/RAM)
                                          └─ ops: beat, inbox/outbox, сверка, резервы, ретеншн
```

| Слой | Технология | Версия (lock-файлы) |
|---|---|---|
| Frontend | Next.js App Router, React, TypeScript | next 15.5.28, react 19.2.0 (`frontend/package-lock.json`) |
| Backend | Python, FastAPI, SQLAlchemy 2, Alembic, Pydantic 2 | Python 3.13, fastapi 0.162.0, sqlalchemy 2.1.6, alembic 1.20.1 (`backend/uv.lock`) |
| DSP | NumPy, SciPy, FFmpeg/ffprobe (soxr) | numpy 2.5.4, scipy 1.18.1, ffmpeg 6.1.1 |
| Очередь | Celery + Redis | celery 5.6.3 |
| Хранилище | S3-совместимое (MinIO) или локальная ФС | boto3 |
| SDK | TypeScript | typescript 5.9.3 |

Next.js 15 выбран вместо 16, так как это проверенная стабильная ветка с известным API (асинхронные `params`, middleware); переход на 16 — отдельная задача.

## Ключевые решения

1. **Один владелец бизнес-логики.** Деньги, доступ, статусы, остатки, тарифы и совместимость считает только backend. Next.js лишь отображает и вызывает API. Цена при покупке не передаётся из браузера: клиент указывает только `app_id` и тип (`one_time`/`subscription`/`free`).
2. **Аутентификация.** Cookie-сессия (`httpOnly`, `SameSite=Lax`, `Secure` в production) + CSRF (double submit: `nap_csrf` cookie == заголовок `X-CSRF-Token`, сверяется с серверной сессией). Пароли — Argon2id. Ограничение попыток входа по хешу e-mail. Developer-ключи `napk_…` хранятся только хешем, имеют scopes и отзыв; ключом нельзя управлять ключами и нельзя получить права модератора/админа. Устройство получает отдельный токен `napd_…` (роль «сервис устройства»).
3. **Роли.** `RoleGrant` на каждую роль отдельно; продавец/оператор исполнения дополнительно привязаны к конкретному `Seller` через `SellerMember`. Права проверяются на сервере в каждом обработчике; чужие объекты возвращают `404` (не раскрываем существование).
4. **Хранилище.** Ключи объектов генерирует сервер (`kind/owner/uuid.ext`), пользовательские имена — только для отображения. Загрузка — одноразовый тикет с ожидаемым размером и SHA-256; одобренный (immutable) объект нельзя перезаписать. Выдача — подписанные HMAC короткоживущие ссылки (`/api/v1/files/<token>`, TTL 300 с) после проверки прав; для S3 API проксирует объект (бакет остаётся во внутренней сети, Range поддерживается).
5. **Конвертация вне HTTP.** API создаёт задание (идемпотентно по `Idempotency-Key`), worker берёт его через атомарный `UPDATE … RETURNING` с lease. Состояние и прогресс — в PostgreSQL; интерфейс опрашивает (polling). Подробно — `docs/dsp.md`.
6. **Внешние системы ≠ транзакция БД.** Webhooks: проверка подписи на сыром теле → уникальная запись в `webhook_inbox` → `200` → обработка с повтором и дедупликацией; событие «не по порядку» остаётся в inbox и повторяется. Исходящие вызовы (возвраты, выплаты, уведомления, передача поставщику) идут через `outbox`. Зависшие попытки оплаты сверяются (`reconcile_attempts`).
7. **Финансовые инварианты в БД.** Журнал проводок неизменяем (триггеры запрещают UPDATE/DELETE), каждая транзакция сбалансирована по валюте (отложенный constraint trigger), `business_ref` уникален. Остатки: `CHECK (on_hand − reserved − allocated ≥ 0)`. Один активный сеанс на устройство — частичный уникальный индекс.
8. **Конфигурации окружения.** `NAP_ENV=demo|test|production`. В production запуск с mock-платежами или mock-доставкой невозможен (валидация настроек), тестовые эндпоинты-симуляторы `/api/v1/test/*` не монтируются.
9. **Логи и приватность.** JSON-логи с `request_id`/`job_id`; подписанные URL в пути редактируются; аудит фильтрует поля с адресами, телефонами, токенами, ответами анкет. Удаление профиля обезличивает пользователя без каскадного удаления заказов и журнала.

## Существенные допущения

- Валюта демо — EUR; конвертация валют не входит в MVP; заказ и цена всегда в одной валюте.
- Налог в demo = 0; база распределения 30/70 — стоимость контента без отдельно учтённого налога, минус возвраты.
- Период удержания выплат и grace period подписки по умолчанию 0 (настраиваются).
- Продажи оборудования в demo — «собственная продажа оператора» (`Seller.kind=operator`), расчёты с поставщиками — отдельная политика (`settlement_policy`), к цифровой доле 70/30 отношения не имеют.
- Mock-перевозчик отправляет только со склада в DE; тарифы — воспроизводимая тестовая таблица зон; для международных этикеток он требует латиницу (это правило mock-перевозчика, а не всех стран).
- Условия поставки по умолчанию DAP: пошлины платит получатель, их сумма неизвестна и не показывается нулём.
- Анкета `state-v1` (расслабленность, напряжение, бодрость, 0–10) одинаковая до и после.
- Протокол кресла NAP SYSTEM не предоставлен: `NapChairAdapter` отказывает во всех командах, используются симулятор и веб-проигрыватель в наушниках.
- Отправка e-mail: уведомления рендерятся на языке заказа/профиля и сохраняются (видны в профиле); SMTP-транспорт — production-зависимость.
