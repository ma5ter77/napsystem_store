# Кандидат безопасного выпуска — 01.11.2026

Статус: локальный кандидат, НЕ установлен. Docker/HTTP/БД на реальном сервере
не проверены. Production, DNS, nginx и 18641 этой работой не менялись.

## Границы

Новый release_control.py заменяет прежний безусловный `compose up --build`.
Bash-файлы — тонкие оболочки. Без `--apply` выполняется только проверка архива,
ожидаемой версии и хеша окружения: никаких Docker, HTTP, распаковки или переключений.
Plan-only НЕ доказывает достаточность ресурсов, правильность Docker и успешный запуск.

Кандидат предназначен только для ЗАКРЫТОЙ демонстрации: `NAP_ENV=demo`, локальное
хранилище, отдельная PostgreSQL, loopback web-port. Публичный доступ к demo-аккаунтам
с известными паролями недопустим: ограничение доступа к будущему vhost — отдельный
проверенный серверный шаг. `--closed-demo` — подтверждение оператора, не firewall.
Production-режим и S3 этим runner намеренно не поддерживаются до отдельной приёмки.

## Что защищено

- Полный commit SHA + отдельно одобренный SHA-256 архива `git archive`.
  Комментарий SHA в tar связывает архив с заявленной версией; это не подпись автора.
  Доверять нужно проверенному SHA-256 из сборки одобренного Git-коммита.
- Архив только исходников, максимум 256 MiB распакованного содержимого;
  запрещены traversal, links/devices, дубли, .git, .env и каталоги зависимостей.
- Атомарный общий lock на deploy/rollback; не истекает автоматически. Состояние
  операции сохраняется до переключения. После SIGKILL/обрыва нужна сверка оператором.
- Ожидаемый current SHA, хеш текущих файлов, frozen compose/env, image IDs,
  фактические образы и окружение контейнеров. Изменения останавливают операцию.
- Минимум 8 GiB свободного диска и 4 GiB MemAvailable перед применением.
  Это консервативный допуск кандидата, НЕ доказанная ёмкость/нагрузочная цель.
  VM 18641 с 3 GiB не подходит и не используется.
- Новый выпуск не перезаписывает существующий каталог. Сборка до изменения служб;
  runtime и откат используют записанные image IDs, `--no-build --pull never`.
- Обновление/откат НЕ запускают migrate и НЕ меняют инфраструктурные службы.
  Изменение миграций, compose topology или окружения требует отдельного плана.
  Изменение моделей без миграции должно быть поймано CI `alembic check` до выпуска.
- Проверка /ru, /en, /ready и точного /version.build с ограниченным ожиданием.
  current меняется после готовности; state хранит предыдущую версию и конфигурацию.
- При неуспехе обновления восстанавливаются предыдущие образы/конфигурация и
  проверяется готовность. Если восстановление тоже не удалось, блокировка остаётся.
- При неуспехе первоначальной demo-инициализации службы останавливаются, тома
  сохраняются; повтор seed/migrate и автоматический restore запрещены.

## Подготовка оператором — отдельное разрешение на серверные действия

Нужны Linux, Python 3.10+, Docker с Compose >=2.24.4 (`!reset`/`!override`), отдельный
каталог /srv/nap-store с releases/, shared/, control/, приватный shared/.env (600).
Каталоги должны принадлежать назначенному оператору, без symlinks в пути.
Файл state/control содержит конфигурацию с секретами: права 600/700, не отправлять
в GitHub, Telegram или журнал. Старые releases, control-файлы и Docker image IDs
сохранять до окончания окна отката. Никаких `docker image prune` во время выпуска.

Отдельный Linux-пользователь в обычной группе docker всё равно имеет фактически
административные возможности через Docker daemon. Для общей машины с платформой
нужен отдельно согласованный вариант: отдельный VPS, rootless Docker или ограниченный
runner администратора. Создание такого доступа НЕ входит в этот кандидат.

До первого bootstrap: проверить, что на сервере нет контейнеров/томов nap-store,
порт свободен; заранее provision инфраструктурные образы postgres/redis/backup.
Конвертер/БД и резервирование не имеют доказанной изоляции ресурсов от платформы.
Проверить лимиты CPU/RAM/диска, права volumes и резерв вне сервера в изолированной среде.
`--bootstrap-demo` явно разрешает одно первоначальное выполнение demo seed/migrations.
После неуспеха не снимать lock и не повторять команду вслепую.

## Шаблоны команд (НЕ запускать сейчас)

Из чистой проверенной рабочей копии собрать архив, затем получить SHA-256:

```bash
git archive --format=tar.gz --output=store-COMMIT.tar.gz COMMIT
sha256sum store-COMMIT.tar.gz
```

Вместо COMMIT — полный одобренный SHA, вместо остальных заглавных значений —
проверенные значения. SHA окружения получают локально на сервере, содержимое не печатают.

```bash
bash ops/cohost/deploy-cohost.sh --archive /ABS/store-COMMIT.tar.gz --sha COMMIT \
  --archive-sha256 ARCHIVE_SHA256 --expected-current CURRENT_SHA --env-sha256 ENV_SHA256
```

Это только план. Применение после отдельного разрешения добавляет `--apply --closed-demo`.
Для первой закрытой demo-установки: `--expected-current none --bootstrap-demo`.
Для следующих выпусков нужна согласованная совместимость БД и свежий проверенный
резерв; этот runner не делает backup и не выдаёт отсутствие миграций за полный DR-план.

```bash
bash ops/cohost/rollback-cohost.sh --expected-current FAILED_OR_CURRENT_SHA \
  --env-sha256 ENV_SHA256
```

Откатывается записанный `previous`, показанный оператору в release-state.json.
Сначала план, затем отдельно разрешённое `--apply --closed-demo`. Откат не перестраивает
образы и не делает downgrade/restore БД. Если данные/схема несовместимы — остановиться.

## Оставшиеся проверки перед серверной установкой

1. CI PR должен быть зелёным на точном SHA; `master` не сливать автоматически.
2. На одноразовом Linux/Docker стенде: реальный bootstrap, успешное обновление,
   искусственный отказ /ready, восстановление старых образов, rollback, занятый порт,
   дрейф файлов/env, два параллельных оператора и обрыв процесса. Только синтетическая БД.
3. SQL/медиа до и после, отсутствие повторного seed при обновлении, сохранность backup.
4. Согласовать DNS/TLS/vhost, закрытый доступ, пользователя, ресурсы и rollback первого запуска.
5. Выбрать отдельный режим/приёмку реальных продаж; mock/demo не переводить в production
   простой заменой домена. Не использовать старый ops/deploy-vps.sh на сервере платформы.

Офлайн fake-engine тесты подтверждают ветвления/отказы контроллера, но не Docker,
systemd, Postgres, фактические ресурсы и эксплуатационную безопасность сервера.
