# Цифровые покупки, подписки, распределение 30/70

Код: `backend/app/services/billing.py`, `services/money.py`, `adapters/payments.py`.

## Сущности

`DigitalOrder` (заказ) · `PaymentAttempt` (попытка оплаты, `context=digital|hardware`) · `Subscription` + `SubscriptionPeriod` (оплаченные интервалы) · `Entitlement` (право) · `RevenueShare` (распределение по продаже) · `LedgerTransaction/LedgerEntry` (журнал) · `Refund` · `Payout` · `WebhookInbox` / `Outbox`.

## Поток оплаты

1. `POST /checkout/digital {app_id, kind}` — сервер берёт активную цену, создаёт заказ (снимок ставки комиссии `commission_bps`), коммитит, затем вызывает `PaymentProvider.create_checkout` с ключом идемпотентности `digital:<order_id>`.
2. Пользователь уходит на страницу провайдера. **Redirect не подтверждает оплату.**
3. Провайдер присылает webhook → проверка подписи на сыром теле → уникальная запись в inbox → `200` → обработчик:
   - `checkout.succeeded` (разовая): заказ `paid`, право `one_time` (уникально по `order_id`), проводка `sale:<order_id>`, `RevenueShare`, уведомление на языке заказа;
   - подписка: доступ выдаёт только `invoice.paid` — создаётся период (уникальный `invoice_ref`), заказ периода, проводка, право `subscription` (уникально по подписке).
4. Дубли (тот же event id или другой id с тем же смыслом), конкурентная доставка и иной порядок не создают вторых прав и денег: уникальные ключи + `SELECT … FOR UPDATE` + идемпотентные переходы. Событие, ссылающееся на ещё неизвестный объект, оставляется в inbox с `retry_later` и обрабатывается повторно (beat каждые 30 с).

## Подписки

Подписка — на отдельное приложение. Доступ есть, если существует неотозванный период, покрывающий «сейчас» (+ grace, по умолчанию 0). `paid_until` = максимум концов неотозванных периодов. Отмена автопродления (`cancel_at_period_end`) сохраняет доступ до `paid_until`. Неудачное продление → `past_due`, оплаченный период не аннулируется. Возврат относится к конкретному периоду: полный — период `refunded`, остальные интервалы не трогаются.

## Деньги и распределение

- Суммы — целые числа в минимальных единицах, валюта рядом с суммой, транзакция журнала в одной валюте (проверяется триггером).
- База — подтверждённая стоимость контента без отдельно учтённого налога (в demo налог 0), за вычетом возвратов.
- `platform = (net·bps + 5000) div 10000` (half-up), `developer = net − platform`.
- При каждом возврате доли **пересчитываются от накопленного остатка** и проводится разница — округление не копится: 10 000 → 3 000/7 000; возврат 4 000 → 1 800/4 200; ещё 6 000 → 0/0.
- Комиссия платёжного оператора — расход платформы (`platform:fees_expense`), долю автора не уменьшает.

Проводки:

| Событие | Дебет (+) | Кредит (−) |
|---|---|---|
| Продажа | `cash:<provider>` | `platform:revenue`, `developer:<id>:payable`, `tax:payable` |
| Возврат | `platform:revenue` Δ, `developer:<id>:payable` Δ | `cash:<provider>` |
| Выплата создана | `developer:<id>:payable` | `developer:<id>:payout_in_transit` |
| Выплата подтверждена | `…:payout_in_transit` | `cash:<provider>` |
| Выплата не прошла | `…:payout_in_transit` | `developer:<id>:payable` (сторно) |

Журнал неизменяем; исправления — только обратными/корректирующими транзакциями; `business_ref` уникален для каждой внешней операции.

## Возвраты и выплаты

Возврат: `Refund(pending)` + outbox → `PaymentProvider.refund` (ключ идемпотентности `refund:<id>`) → webhook `refund.succeeded` → проводки. Сумма возвратов ≤ подтверждённой оплаты (проверка в сервисе и `CHECK` в БД). Полный возврат разовой покупки отзывает право, частичный — сохраняет.

Балансы разработчика: начислено (accrued), ожидает (до `available_at` = оплата + период удержания), доступно, в пути, выплачено. Возврат после выплаты делает баланс отрицательным; он показывается и блокирует новые выплаты до погашения будущими продажами. `paid` наступает только после подтверждения провайдера; mock-выплаты помечены `mock=true`.

## Провайдеры

- **MockPaymentProvider** — рабочий, только вне production. Тестовая страница оплаты (`/mock-checkout/<ref>`) с кнопками «Оплатить (тест)»/«Отклонить (тест)» генерирует **подписанные webhooks**, которые проходят ту же проверку и inbox, что и у реального провайдера. Симуляторы продления/неудачного продления: `POST /api/v1/test/subscriptions/{id}/renew`.
- **StripeProvider** — референсный адаптер Checkout/Billing (test mode): Checkout Sessions (`payment`/`subscription` с `price_data`), идемпотентные ключи, отмена автопродления, refunds, Connect transfers для выплат (при наличии подключённого аккаунта `users.payout_account`, иначе выплата помечается неуспешной и сторнируется), проверка `Stripe-Signature`, нормализация `checkout.session.*`, `invoice.paid|payment_failed`, `customer.subscription.deleted`, `refund.*`. Контрактные тесты (подпись + нормализация) выполняются без сети; live sandbox-тест запускается только при `NAP_STRIPE_SECRET_KEY` и без него отмечен **not run**.

Другой оператор подключается реализацией того же протокола `PaymentProvider` (`create_checkout`, `retrieve`, `cancel_subscription`, `refund`, `payout`, `verify_webhook`, `event_id`, `normalize`).
