# Нагрузочное тестирование (NAP-050)

Инструмент: `ops/loadtest.py` — каталог (анонимный просмотр), покупки (регистрация → покупка → тестовая оплата → библиотека), параллельные конвертации. На каждом уровне параллельности выдаёт запросы в секунду, ошибки, p50/p95/p99. **Предел** — наибольший уровень, на котором p95 < 500 мс и ошибок < 1 %.

```
NAP_RATE_LIMITS_ENABLED=false   # для теста: иначе один генератор — один «пользователь», и его ограничивают по правилам
uv run --project backend python ops/loadtest.py --base http://127.0.0.1:8000 --seconds 30 --concurrency 1,4,16,32 --json load.json
```

Запускать только на демо- или тестовом стенде: в сценарии покупок оплата идёт через тестового провайдера.

## Результаты 01.11.2026 — среда разработки, не целевой сервер

2 vCPU Xeon 2,1 ГГц, 8 ГБ. PostgreSQL, Redis, API, воркеры Celery и генератор нагрузки работают на одной машине, поэтому цифры занижены. Next.js в замер не входил — запросы шли напрямую в API.

### Найдено и исправлено

Каталог приложений для каждого приложения отдельно запрашивал версию, переводы, категорию и цены — около 6 запросов к базе на карточку, ~250 на страницу при 41 приложении. Список товаров так же запрашивал продавца, категорию, переводы и остаток по каждому варианту.

Теперь данные для всех карточек загружаются пачкой: 7 запросов на каталог и 6 на список товаров, независимо от числа позиций. Тест `test_catalog_lists_use_a_bounded_number_of_queries` не даёт этому вернуться.

| Запрос | До | После |
|---|---|---|
| `GET /catalog/apps?limit=20` (41 приложение) | 230 мс | 18 мс |
| `GET /catalog/apps?q=…` | 190 мс | 17 мс |
| `GET /hardware/products?limit=100` | 100 мс | 16 мс |

### Пропускная способность

| Сценарий | API | Параллельность | Запросов/с | p95 | Ошибки |
|---|---|---|---|---|---|
| Каталог, до исправления | 1 процесс | 4 | 9,7 | 735 мс | 0 |
| Каталог | 1 процесс | 4 / 16 / 32 | 64 / 55 / 53 | 89 / 415 / 832 мс | 0 |
| Каталог | **2 процесса** | 4 / 16 / 32 | 64 / **100** / 98 | 90 / **361** / 721 мс | 0 |
| Покупки | 1 процесс | 1 / 4 / 16 | 13 / **18** / 16 | 37 / **125** / 681 мс | 0 |

**Предел на этой машине:**
- каталог — около **100 запросов/с** при 2 процессах API (16 одновременных клиентов, p95 361 мс);
- покупки — около **18 оплаченных заказов-шагов в секунду** (4 одновременных покупателя, p95 125 мс).

Дальше растёт только задержка: процессор занят целиком, ошибок нет.

**Конвертации** — 4 автора одновременно, трек 60 с, 2 воркера `media`. Все 4 завершены. Ожидание в очереди: среднее 2,6 с, максимум 4,9 с. Обработка: 3,4–3,7 с на задание. Задания выполняются по два одновременно — по числу воркеров; остальные ждут без потерь. Время обработки длинных файлов — `docs/operations.md`, раздел «Benchmark конвертации»: 60 минут обрабатываются ≈ 2 мин 9 с.

### Изменения по итогам

- API запускается в нескольких процессах: `NAP_API_WORKERS`, по умолчанию 2, в Docker-образе и compose. Общие счётчики ограничений лежат в Redis, поэтому лимиты остаются едиными.
- Рекомендация для целевого сервера: процессов API — по числу ядер; воркеров `media` — не больше (ядра − 1), конвертация занимает ядро целиком.

## На целевом сервере (после разрешения на выпуск, NAP-085)

Повторить тот же запуск на store.napsystem.com с отдельной машины-генератора и внести цифры сюда. До этого критерий приёмки «предел RPS на целевом сервере» не закрыт.
