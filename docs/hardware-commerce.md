# Оборудование: каталог, совместимость, BOM, склад, заказы, доставка, исполнение, возвраты

Код: `backend/app/services/hardware.py`, `services/hardware_orders.py`, `services/addresses.py`, `adapters/shipping.py`.

## Каталог и совместимость

Навигация: Приложения / Устройства / Комплекты. Категории: кресла, (вибро)акустика, наушники, контроллеры, датчики, питание, кабели. Карточка: продавец, бренд/модель, SKU, комплектация, характеристики, цена/валюта, наличие или срок изготовления, гарантия, возврат, страна отправления, направления, подготовка, вес/габариты, включена ли сборка. Тексты — отдельные переводы (`translations`, статусы `draft/published`); ID, цена, остаток общие для обеих локалей.

`compatibility`: SKU × (модель NAP SYSTEM | функция) со статусом `verified / vendor_claimed / unverified / incompatible`, источником, проверенной конфигурацией и датой. Правило платформы: стереодинамики ≠ разделение каналов у ушей; совместимость по виброакустике ≠ подтверждённый бинауральный тракт.

## Комплекты (BOM)

- `kit_component` — собирается из компонентов: наличие определяется компонентами; в корзину добавляются компоненты.
- `kit_stock` — готовый складской комплект со своим SKU и остатком; его детали не списываются.
- BOM версионирован (`boms.version`), позиции: обязательные/необязательные, количество, альтернативные совместимые SKU, назначение (наушники, питание, кабели…).
- Подбор (`GET /hardware/kits/{slug}/bom?owned=…&app=…`): статусы `owned/missing/optional`, совместимость, наличие, группы недостающего по продавцам, непокрытые требования приложения, флаг «отдельные заказы». Из карточки приложения — «Подобрать оборудование» (`/kits?app=…`). Цифровая лицензия не возникает от покупки комплекта.
- Состав BOM сохраняется снимком в заказе.

## Заказы

Цифровой и аппаратный checkout раздельны. Корзина делится на заказы по (продавец, склад, валюта) — это видно до оплаты; общей атомарной покупки разных продавцов нет. `HardwareOrder` хранит снимки SKU, цен, BOM, адреса, локали, условий, тарифа/предложения.

Статусы независимы: заказ `awaiting_quote / awaiting_payment / confirmed / cancelled / closed`; оплата `unpaid / pending / paid / partially_refunded / refunded / failed`; исполнение `unfulfilled / processing / partially_shipped / shipped / delivered / exception`.

Оплата — тот же `PaymentProvider`, `context=hardware`. Подтверждение оплаты: `reserved → allocated`, проводка `hw_sale:<id>` на счета продавца (`hardware:<seller>:goods|shipping|fees`) — **без** цифровой доли 30/70; передача поставщику через outbox (`FulfillmentAdapter.submit`).

## Склад

`available = on_hand − reserved − allocated ≥ 0` (CHECK в БД).
- Резерв при создании заказа: все строки заказа атомарно, блокировки в детерминированном порядке; TTL 30 мин; истёкшие резервы освобождает beat.
- Оплата: `reserved → allocated`. Поздняя оплата после истечения: попытка заново обеспечить остаток; если нельзя — заказ оплачен, исполнение `exception` (`stock_unavailable_after_payment`), уведомление и согласование/возврат. Фиктивного наличия нет.
- Передача перевозчику (handover, не покупка этикетки!) одновременно уменьшает `on_hand` и `allocated`. Отмена освобождает ровно один раз (статус резерва).
- Производство под заказ имеет свой срок и не показывается складским наличием.
- Возврат товара увеличивает остаток только после фактической приёмки и проверки (и только принятое к повторной продаже).

## Доставка

До оплаты: проверка адреса (Unicode; обязательные поля по стране; латиница только если её требует перевозчик), склад отправления, маршрут, услуга, ограничения груза (вес/длина/обхват), стоимость/валюта, срок действия тарифа, ориентировочная дата с учётом подготовки (в UI — «оценка, а не гарантированная дата»). Тариф привязан к хешу состава и адреса: изменение адреса/количества требует пересчёта (`rate_stale`), истёкший тариф — `rate_expired`. Неподдерживаемый маршрут/габарит — явная ошибка, нулевая доставка не подставляется. Пошлины при DAP: «не включены, сумма неизвестна, платит получатель».

Крупногабаритное кресло: `freight_mode=custom_quote` → запрос → расчёт поставщика (сумма, срок, срок действия) → принятие покупателем → оплата.

Адаптеры (`ShippingAdapter`: услуги, тарифы, создание/отмена отправления, документы, tracking, проверка и нормализация событий):
1. **MockShippingAdapter** — воспроизводимые зональные тарифы, тестовые PDF-этикетки, подписанные события tracking (источник `simulator`), симуляция таймаута.
2. **Ручной режим** — подтверждённое предложение поставщика, внешнее оформление, загрузка PDF-документов, реальный трек-номер, события от поставщика (`supplier`).
3. **EasyPostAdapter** — референсный test-адаптер (REST, HMAC-подпись webhooks, нормализация `tracker.updated`, повтор после таймаута через сохранённый `shipment id` без повторной покупки). Применимость к любой стране/креслу не предполагается: крупногабарит → ручной freight. Без ключа live-проверка — **not run**.

Создание этикетки идемпотентно: ключ `label:<parcel_id>` фиксируется в БД до вызова перевозчика; повтор после таймаута возвращает ту же этикетку (тест считает покупки = 1). Tracking-события проверяются, сохраняются, дедуплицируются `(parcel, source, external_id)`, неверный порядок сверяется (терминальные статусы и время возникновения). Источник статуса виден покупателю. «Этикетка создана» ≠ отправлено ≠ доставлено; общий статус учитывает все посылки и позиции.

## Исполнение (поставщик)

Оплаченный заказ → «Принять в работу» → упаковочные места (позиции/количества, вес, габариты; нельзя упаковать больше заказанного) → этикетка (адаптер) или ручная отправка → документы → передача перевозчику → события/проблемы. Документы (упаковочный лист / данные инвойса, PDF) строятся из снимка заказа; HS-код только подтверждённый поставщиком, иначе «не указан»; батареи помечаются. Документы доступны покупателю и уполномоченному исполнению, чужим продавцам — `404`. Оператор исполнения видит только назначенные оплаченные заказы и не видит цены.

## Возвраты

Отмена, денежный возврат и возврат товара — разные процессы. Возврат товара: запрос (≤ отправлено − возвращено − в процессе) → решение → обратная отправка (трек) → получение → проверка (принято/на склад) → закрытие. Денежный возврат — отдельными строками (товары/доставка/сборы), каждая ≤ оплаченной, идемпотентно, через провайдера. Возврат оборудования не отзывает отдельно купленное приложение.
