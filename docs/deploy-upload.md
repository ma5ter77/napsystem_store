# Выгрузка магазина на сервер store.napsystem.com

Постоянная инструкция и параметры (инструкция владельца от 01.11.2026). Скрипт: `ops/upload-to-store.sh`
(копия на Mac — `~/Projects/_nap-store-backup-20261031/nap-store-upload.sh`).

## Что разрешено и что нет

- **Разрешено:** загрузить исходный архив проверенного коммита в новую уникальную папку `/srv/nap-store/incoming/upload.XXXXXXXX`
  и проверить контрольную сумму.
- **Запрещено без отдельного утверждения владельца:** распаковывать, устанавливать, запускать, Docker, миграции, deploy/rollback,
  sudo, перезапуск служб, изменение nginx/DNS. Нельзя удалять или перезаписывать файлы на сервере, нельзя использовать `rsync --delete`.
  Нельзя смотреть или менять файлы основной платформы (napsystem.ru / napsystem.com).
- Секреты (приватный ключ, парольная фраза, `.env`) никому не передаются — ни в чат, ни в Telegram, ни в GitHub.

## Порядок (делает скрипт; запускается на Mac владельцем ключа)

```
bash ~/Projects/_nap-store-backup-20261031/nap-store-upload.sh            # master с GitHub
STORE_SHA=<полный SHA> bash ~/Projects/_nap-store-backup-20261031/nap-store-upload.sh   # другой согласованный коммит
```

1. Проверка ключа и входа: `whoami` = napstore, `id`, `test -w /srv/nap-store/incoming`; сверка отпечатка сервера.
2. Выбор коммита: по умолчанию master на GitHub, либо `STORE_SHA`. Коммит должен быть опубликован на GitHub и согласован с владельцем.
   Скрипт сравнивает его с последним проверенным выпуском (`TESTED_COMMIT` в скрипте) и при расхождении требует ввести начало SHA.
   Проверка состава: нет `.env`, ключей, дампов, LFS, submodules, строк, похожих на ключи (`sk_live_`, `whsec_`, `PRIVATE KEY`…).
3. `git archive` → `store-<SHA>.tar.gz` + `.sha256` во временной папке на Mac.
4. На сервере `mktemp -d /srv/nap-store/incoming/upload.XXXXXXXX`, `scp` двух файлов в эту папку.
5. На сервере `sha256sum -c`, сверка SHA-256 с Mac, печать отчёта владельцу (репозиторий, коммит, версия, совпадает ли с проверенным
   выпуском, папка, файлы, SHA-256, ссылка на проверки коммита, ограничения).

**Перед запуском:** убедиться, что нужный PR принят в master, а CI этого коммита зелёный. После каждого нового проверенного выпуска
обновить `TESTED_COMMIT` в скрипте.

## Что дальше (не делается этим скриптом)

Распаковка, установка и запуск — только по отдельному утверждению владельца: точный артефакт, изолированная проверка и серверный
план (`STORE_SAFE_LAUNCH_PLAN_20261101.txt` у владельца; `docs/deployment-store.md` — описание схемы). Перед выпуском оператор ещё раз
сверяет hash и переносит артефакт в своё защищённое хранилище.
