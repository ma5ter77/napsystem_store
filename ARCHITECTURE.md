# Архитектура развёртывания магазина

Как приложение запущено на сервере `nap-store-arm1`: процессы, сети, данные, границы безопасности. Устройство
самого приложения (модули, платежи, конвертер, студия) описано в [docs/architecture.md](docs/architecture.md)
и [docs/architecture/audio-platform.md](docs/architecture/audio-platform.md).

## Общая схема

```
                Интернет (ЕС, США, …)
                       │ 80/443 TCP, 443 UDP (HTTP/3)
              ┌────────▼────────┐  ufw: открыты только 22, 80, 443; fail2ban на SSH
              │      Caddy      │  TLS Let's Encrypt, HSTS, zstd/gzip, без заголовка Server
              └────────┬────────┘
                       │ всё → web:3000
              ┌────────▼────────┐
              │ web (Next.js)   │  страницы (SSR); /api/* проксирует в api по внутренней сети
              └────────┬────────┘
              ┌────────▼────────┐
              │ api (FastAPI)   │  2 процесса uvicorn
              └──┬──────┬───────┘
                 │      │            сеть core (internal: без выхода наружу)
   ┌─────────────▼┐ ┌───▼──┐
   │   postgres   │ │redis │
   │     16       │ │  7   │
   └──────┬───────┘ └──────┘
          │ том pgdata
   ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
   │ worker-media │ │ worker-ops   │ │ backup       │
   │ конвертер,   │ │ webhooks,    │ │ pg_dump +    │
   │ экспорт      │ │ outbox,      │ │ проверка     │
   │ студии       │ │ сверка оплат │ │ восстановл.  │
   └──────────────┘ └──────────────┘ └──────┬───────┘
   том storage: файлы авторов, конвертации,  │
   экспорты студии                           ▼ /srv/nap-store/backups
```

Сети Docker: `core` — внутренняя, без выхода в интернет: postgres, redis, все сервисы приложения. `edge` — для
тех, кому нужен внешний мир: caddy (входящие), api и worker-ops (Stripe, почта), web. База и Redis наружу не
опубликованы; порт публикует только Caddy.

## Сервисы и ресурсы

Сервер: 4 vCPU Ampere, 8 ГБ RAM, 80 ГБ NVMe, swap 2 ГБ. Лимиты заданы в `ops/vps/docker-compose.prod.yml`
(рассчитаны на 4 ГБ, на 8 ГБ остаётся запас):

| Сервис | Образ | Память | Что делает |
|---|---|---|---|
| caddy | caddy:2.8-alpine | 128 МБ | HTTPS, заголовки безопасности, сжатие; весь трафик → web |
| web | ghcr.io/ma5ter77/nap-store-web | 512 МБ | интерфейс (Next.js), прокси `/api/*` → api |
| api | ghcr.io/ma5ter77/nap-store-backend | 768 МБ | REST API, 2 процесса uvicorn |
| worker-media | то же | 1 ГБ, 1,5 CPU | конвертация, рендер и экспорт аудиостудии (очередь `media`) |
| worker-ops | то же | 512 МБ | Celery beat: webhooks, outbox, lease, резервы, сверка оплат |
| postgres | postgres:16-alpine | 768 МБ | база (том `pgdata`) |
| redis | redis:7-alpine | 192 МБ | очередь задач, лимиты запросов |
| backup | postgres:16-bookworm | 256 МБ | ежедневный дамп с проверкой восстановления, архив файлов |
| migrate | образ backend | 1 ГБ | запускается выкладкой: `alembic upgrade head` и сид демо |

Все образы собираются под `linux/amd64` и `linux/arm64` под одним digest. Сервер скачивает свою архитектуру,
поэтому магазин переезжает на x86 или Arm без изменений.

## Каталоги на сервере

```
/opt/nap-deploy/            napdeploy.py (root, только чтение для napdeploy) + config.json
/srv/nap-store/
  shared/.env               настройки и секреты приложения (600, napdeploy)
  releases/<sha>/           набор файлов выпуска (compose, Caddyfile, скрипты), последние 5
  state/state.json          текущий, предыдущий выпуск и история
  backups/                  pre-deploy-*.dump (5), nap-*.dump (14 дней), storage-*.tar (2 дня), last-status.json
Тома Docker: pgdata, storage, jobs, caddy_data, caddy_config
```

## Выкладка и откат

1. CI на master зелёный → последний job вызывает `deliver-vps`.
2. Образы backend и web собираются (кэш слоёв GitHub) и публикуются в GHCR. Сервер принимает только образы
   `ghcr.io/ma5ter77/nap-store-*` и только по digest.
3. `ci_deploy.py` подключается как `napdeploy` по закреплённому ключу хоста; ключ может запускать только
   `napdeploy.py gate`.
4. `napdeploy.py`: проверка набора файлов и compose (запрещены privileged, cap_add, devices, host network/pid,
   монтирование вне выпуска и backups, публикация портов кроме Caddy) → скачивание образов временным токеном
   задания → дамп БД → миграции → переключение → ожидание готовности до 180 с → при ошибке возврат
   предыдущего выпуска.
5. Откат (`rollback`) возвращает предыдущий выпуск без изменения схемы БД, поэтому миграции совместимы назад.

## Безопасность

- Вход на сервер только по ключу, root — без пароля, firewall и fail2ban, автообновления безопасности.
- Секреты приложения существуют только в `shared/.env` на сервере. Установщик генерирует их там же.
- Демо-аккаунты на публичном сервере не принимают документированный пароль (`NAP_PUBLIC_DEMO=true`).
- Cookie сессий `Secure`, CSRF-токен, лимиты запросов в Redis. Подписанные ссылки на файлы живут 5 минут.
- Логи в отчётах GitHub очищаются от строк, похожих на секреты.

## Ограничения текущей схемы

- Один сервер: при его падении магазин недоступен до восстановления (Hetzner Backups или новый сервер,
  см. OPERATIONS.md).
- Бэкапы лежат на том же сервере, пока не подключено внешнее хранилище.
- Нет внешнего мониторинга с оповещениями (метрики есть: `/api/v1/metrics`).
- Масштабирование: сначала больше сервер (CAX31, 8 vCPU / 16 ГБ — через Rescale), затем файлы в S3-хранилище
  (`NAP_STORAGE_BACKEND=s3`) и отдельный сервер под worker-media. Код к этому готов, см. COSTS.md.
